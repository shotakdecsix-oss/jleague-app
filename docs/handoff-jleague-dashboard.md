## 目的

湘南ベルマーレを応援するためのスマホ向けダッシュボードアプリを作る。ニュース・試合結果・試合予定を1画面で追えるようにするのが出発点だったが、設計を進める中で、**J1〜J3の全60クラブから応援クラブを選べる汎用的な作り**にすることに決めた。湘南は「デフォルトの推しクラブ」であって、ハードコードの前提ではない。

差別化機能として、**昇格確率のモンテカルロシミュレーション**と、**過去に在籍したOB選手の移籍先での動向追跡**を入れたい。湘南は2025年J1で19位となり2026/27はJ2所属なので、昇格レースを追うことが当面の主軸になる。

## 前提・決定事項

**課金しない。** これが最大の制約。無料で成立する構成に絞る。

**データソースは TheSportsDB（無料APIキー `123`）に確定。** 認証不要でブラウザから直接叩ける。ただしコミュニティ運営DBなので、表記の古さ・カバレッジの穴は前提として設計する。

**取得は `eventsround.php` 一本に統一する。** 他のエンドポイントは信用しない（理由は末尾）。

**順位表はAPIから取らず、試合結果を積み上げて自前計算する。** これが昇格確率シミュレーションの入力にもそのまま使える。

**表示名（クラブ名・スタジアム名）はすべて自前マスタで持つ。** APIの英語名しか信用せず、日本語表示は全部マスタ経由。

**構成**: GitHub Actions で定期バッチ → 整形済みJSONをリポジトリにコミット → フロントは静的JSONを読むだけ。CORS回避・レート制限対策・表示高速化が同時に解決する。

**Jリーグ公式由来のデータ（`data/processed/club_extra.json`、`data/tmp/` 配下のHTML）は非公開前提。** 公式サイトの利用規約が「文章・画像等の無断での複製・転載」を禁じているため、GitHub Pages等で公開する場合はこれらを配信対象から外し、フロントは公式へのリンクのみに戻すこと。TheSportsDB由来のデータ（`*_matches.json` / `*_standings.json` / `*_simulation.json`）はこの制約の対象外。

**日付・時刻は `strTimestamp`（UTC）のみを信頼する。** `dateEvent` / `dateEventLocal` / `strTimeLocal` は一切参照しない。理由は下記の検証結果を参照。

**必須のデータ処理ルール**

- フィルタ: `strSeason == "2026-2027"` かつ `intRound != "0"` （春開催の「J2・J3百年構想リーグ」とカップ戦の混入を排除するため）
- 時刻・日付: `strTimestamp` はUTC。**+9時間してJST変換し、日付・時刻ともここから導出する**（`scripts/time_utils.py` に実装済み）。`dateEvent` / `dateEventLocal` / `strTimeLocal` は使わない
- 完了判定: `strStatus == "FT"` かつ `intHomeScore` が非null
- シーズン文字列はフォールバック処理を入れる（`2026-2027` が空なら `2026` を試す）

### 日付フィールドの信頼性検証: 重要な発見

J3第1節の「FC琉球 vs ギラヴァンツ北九州」戦（`strStatus: "NS"`、未消化）で `dateEvent`(9/9)と`dateEventLocal`(8/8)が1ヶ月ずれていた。`strTimestamp` を確認したところ `dateEvent` 側（9/9）と整合しており、**延期の日程差し替えが `strTimestamp`/`dateEvent` には反映されたが `dateEventLocal` だけ更新されずに取り残された**典型例と判断できた。

これにより2点が確定した:
1. `strTimestamp` のみを信頼する既存方針は正しく、`dateEventLocal`のような他フィールドを混ぜると壊れる
2. **延期試合は実在する** → 順位表計算では `intPlayed`（消化試合数）を必須表示にする。勝点だけの比較は「1試合未消化で勝点3差」を誤読させるため、昇格争いの文脈では致命的

### 新規追加したガード（レート制限対策の一環）

`scripts/fetch_utils.py` に、複数節をまとめて取得する際の共通ロジックを実装:

- 弾かれ方を `OK` / `EMPTY`(events null or []) / `HTTP_ERROR` / `TIMEOUT` / `BAD_JSON` に分類してログ出力
- 全38節は日程確定済みのため、正常なら全節でイベントが返るはず → `EMPTY` は「その節に試合が無い」ではなく異常シグナルとして扱う
- **N節連続で異常が続いたら処理を中断するサーキットブレーカー**（デフォルト3節連続、`max_consecutive_bad` で変更可）。壊れたJSONを静かにコミットする事故を防ぐ
- sleep秒数は `sleep_between` 引数で外部から調整可能（PC側のレート制限実測結果を反映する想定）
- オフラインでの動作確認済み（モックfetch関数で3節連続異常→中断を検証）。実際のAPIに対する動作はまだ未検証（下記「進行中」参照）

## 未解決の論点

（元の内容から変更なし）

**OB選手リストの保存先が未決定。** アプリ内で登録・管理したいが、RSS取得はCORSの都合でサーバー側（GitHub Actions）でやる必要があり、「リストは端末内・取得はサーバー側」だとサーバーが誰を追うべきか分からないという矛盾がある。候補は3つで、(1) リストもリポジトリのJSONに置きアプリからGitHub API経由で更新、(2) CORSプロキシ経由でブラウザから直接RSS取得、(3) Cloudflare Workersを立てる。**個人利用なら(1)が最も壊れにくいという結論に傾いている**が未確定。

**試合スタッツが取れない。** TheSportsDBにはシュート数・支配率・選手スタッツが無い。分析要件を2層に分けて整理した：

- Tier 1（スコアだけで可能・実装対象）— ポアソン回帰による攻撃力/守備力レーティング、対戦相手補正後の実力値、ホームアドバンテージ推定、期待勝点と実勝点の乖離、残り日程難易度、昇格確率モンテカルロ
- Tier 2（Jリーグ公式のスクレイピングが必要・後回し）— シュート数、枠内率、支配率、選手個人スタッツ

Tier 2に着手する場合は、事前にJリーグ公式のHTML構造とJS描画の有無、および利用規約の確認工程を挟むこと。

**マスタの精度に不安が残る箇所**

- カターレ富山の会場ID（j2マスタ内）は推測値で `unverified: true` フラグ付き
- レイラック滋賀FCの会場（`unverifiedVenue: true`）は実際の試合データで要確認
- スタジアム名全般はネーミングライツで変わりやすく、自信度が低い
- 味の素スタジアムはFC東京と東京Vが共用。会場から主催クラブを逆引きする処理を入れる場合は例外扱いが必要

## 試合経過機能の調査（第6弾B、2026-08-18時点・調査継続中）

速報タブ(C)の実装前に必須の調査。3経路とも完全には決着していない。

**調査1: jleague.jpの試合系ページに埋め込みJSONがあるか**

- `https://www.jleague.jp/match/j1/2026/082102/`（柏vs長崎、第3節、2026/8/21 19:00キックオフ）は**実在する正規のページ**で、`club`ページと同じNext.js(`_next/image`)アセット構成。埋め込みJSON抽出手法が効く可能性が高い。ただし調査時点(8/18)はまだキックオフ前なので、スコア・経過時間・イベント欄の中身は確認できていない。**8/21のキックオフ後にHTMLを取り直して`self.__next_f`の中身を見る必要がある。**
- `https://www.jleague.jp/match/section/j2/3` は**実在しない**。アクセスすると`/j1/match/`（今週の日程一覧）にフォールバックされた。個別試合ページのURL(6桁コード)は、この日程一覧ページのhrefから拾える方式で正しい（`/match/j1/2026/082102/` 等が実際にリンクとして出ていた）。**節ページのURLパターンは要再調査**（`/j1/match/`のクエリパラメータで節を指定する形かもしれない）。
- `https://www.jleague.jp/sp/game/` は**別のテンプレート系統**（`/img/sp/common/...`という旧来のパス構成で、`_next/image`が使われていない）。同じ埋め込みJSON手法が効くかは未確認、おそらく効かない可能性が高い。しかも「試合速報は試合日までお待ちください。当日午前0時に切り替わります」と表示され、**試合が無い日は空**（8/18時点で内容確認不可）。
- いずれも `mcp__workspace__web_fetch` はMarkdown変換された内容しか返さず、`<script>`タグの中身（生HTML）は見えない。**`scripts/save_sample_html.py` に3ページぶんのターゲットを追加済み**（次回ユーザーのPCで実行してもらう必要あり、できれば8/21のキックオフ後）。

**調査2: CORSヘッダーの有無**

未確認。`web_fetch`はレスポンスヘッダーを`Content-Type`程度しか見せないため、`Access-Control-Allow-Origin`の有無が分からない。**ユーザーに、実際にアプリを開く環境（`http://localhost:8000`等）のブラウザ開発者コンソールで下記を実行してもらうのが確実**:

```js
fetch("https://www.jleague.jp/match/j1/2026/082102/")
  .then(r => console.log([...r.headers.entries()]))
  .catch(e => console.log("CORS等で失敗:", e));
```
成功してヘッダーが読めれば直接ポーリング可、`TypeError: Failed to fetch`ならCORS不可でローカルバッチ方式(`fetch_live.py`)が必要。

**調査3: TheSportsDBのライブスコア**

`https://www.thesportsdb.com/api/v1/json/123/livescore.php?s=Soccer` は**実際に動作を確認済み**（2026-08-17 17:44 JST時点、Coppa Italia/ロシア2部/ジョージア1部など多数のリーグのライブスコア・経過時間・ステータスが返ってきた）。また `search_all_leagues.php?c=Japan&s=Soccer` で **J1(idLeague=4633)/J2(4824)/J3(4967)がいずれも登録済みリーグとして存在する**ことを確認した（`strCurrentSeason`も"2026-2027"等、今シーズンを指している）。

ただし確認できたのはこの2点まで。**肝心の「Jリーグの試合中にlivescoreへ実際に載るか」はまだ未確認**（調査時点でJリーグの試合が無かったため）。次のJリーグ開催時刻（2026-08-21(金)19:00 柏vs長崎、または2026-08-22(土)19:00の試合群）に再度叩いて確認する必要がある。**この確認用のスケジュールタスクを設定済み**（8/21 19:05 JSTに自動実行）。

**現時点の暫定的な見立て**: TheSportsDB経由(調査3)が確認できれば、CORS全面許可の実績があるAPIなのでPC不要でフロントから直接ポーリングできる可能性が高く、最もきれいな結末になる。ただし確定するまでは、`fetch_live.py`(ローカルバッチ方式)を前提にCの設計を進めるのが安全。**C(速報タブ)の着手は、この3つの調査が出揃ってから。**

## 環境まわりの注意（次セッション向け）

**ファイル生成は最初からWriteツールで行うこと。** bashで `cp`/`touch` 等を使ってワークスペースフォルダ内にファイルを作ると、そのファイルは後から Write/Edit ツールで編集できなくなる（`EPERM: operation not permitted, rename ...`）。今回3つのマスタJSONがこれに当たり、一度 `allow_cowork_file_delete` で削除してから Write ツールで作り直す必要があった。次に同じ轍を踏むと同じだけ時間を溶かすので注意。

**サンドボックスのbashから thesportsdb.com へは直接アクセスできない**（プロキシで403）。`mcp__workspace__web_fetch` 経由なら到達できるので、単発の検証はそちらを使う。114リクエスト連続のような負荷テストはユーザーのローカル環境で行う。
