# 緊急修正指示：増分取得が既存データを破壊している

対象: `scripts/fetch_batch.py`（＋セーフガードを `scripts/build_ics.py` にも追加）

## 症状

アプリの日程・スコア・順位のいずれにも**第1節の結果が出ない**。

## 実際の被害（症状より深刻）

第1節だけの問題ではない。**第6節以降も全部消えている。**

| ファイル | 正常時 | 現在 |
|---|---|---|
| `j1_matches.json` | 380件（1〜38節） | **40件（2〜5節のみ）** |
| `j2_matches.json` | 380件 | **30件（2〜4節のみ）** |
| `j3_matches.json` | 380件 | **30件（2〜4節のみ）** |
| `calendar.json` | 1140件 | **100件** |
| `j1_standings.json` | basedOnMatches 20 | **10**（1節ぶんのみ） |
| `j1_simulation.json` | remainingMatches 360 | **30** |
| `ics_state.json` | CONFIRMED 1140 | **CANCELLED 1040 / CONFIRMED 100** |

とくに深刻なのが下2つ。

- **シミュレーションが「全4節のシーズン」として昇格確率を計算している。** 出ている確率は完全に無意味。
- **ics の1040試合が `STATUS:CANCELLED`（seq 0→1）になった。** カレンダーを購読している人がいれば、1040件のキャンセル通知が飛ぶ。

`data/history/j1_probability_history.json` の 8/21 のスナップショットも `basedOnMatches: 10` のゴミが入っている（これは後述のとおり自動修復される）。

## 発生源

コミット `a6fc190 auto: データ更新 2026-08-21 14:47 JST` — **第11弾の Actions が初めて自動実行された回**。直前の `cae2935`（第11弾コミット）までは380件あった。

## 根本原因

`scripts/fetch_batch.py` の増分取得（第11弾で追加した `--incremental` / `determine_incremental_rounds()`）が、**取得した節だけでファイルを丸ごと上書きしている。既存データとマージしていない。**

`load_existing_matches()` は「どの節を取得すべきか」を判定するためだけに使われており、書き出し（277行目付近の `out_path.write_text(...)`）では取得結果だけから `out` を組み立てている。

結果、「2〜5節を取得した」＝「2〜5節しか存在しない」というファイルになる。

## 1. 復旧手順（この順番で）

### 1-1. matches を最後の正常なコミットから戻す

```
git checkout cae2935 -- data/processed/j1_matches.json data/processed/j2_matches.json data/processed/j3_matches.json
```

**PowerShell で `git show ... > file` を使わないこと。** PowerShell 5.x のリダイレクトは UTF-16LE で書き出すため JSON が壊れる。上の `git checkout` なら git 自身がファイルを書くので安全。

これで8/21 14:47以降に取得した第2節の内容は一旦失われるが、2章の修正後に増分取得を回せば取り直される。

### 1-2. 先に2章の修正を入れる

**修正前に `update_all.py` を回さないこと。** 同じ事故が再発する。

### 1-3. 全体を再計算する

```
python scripts/update_all.py
```

これで matches → calendar → standings → simulate → stats → build_dist（内部で build_ics）まで通る。

### 1-4. 自動的に直るもの

- **`probability_history`**: 同じ日付は最後の値で上書きする仕様（第8弾）なので、8/21 のゴミは正しい値に置き換わる。手で触らないこと。
- **`ics_state.json`**: `upsert` は matches に存在するイベントを無条件で `CONFIRMED` に戻し、status が変わったので `seq` を 1→2 に上げる。購読者側にも正しく反映される。

### 1-5. `ics_state.json` を git で戻してはいけない（重要）

復元したくなるが、**絶対にやらないこと。**

配信済みの ics には既に `SEQUENCE:1` の CANCELLED が乗っている。`ics_state.json` を `seq:0` の状態に戻すと、以後の生成が `SEQUENCE:0` または `1` になり、**購読者のカレンダーは「より新しい seq でない」として更新を無視する。** キャンセル状態が永久に残る。

今の（壊れた）状態のまま build_ics を走らせるのが正解。seq が 2 に上がることで初めて上書きできる。

## 2. 恒久対策

### 2-1. 増分取得時は既存データとマージする（本体の修正）

書き出し前に、既存の matches と取得結果を `idEvent` をキーにマージする。

```
1. load_existing_matches(league) で既存を読む（無ければ空）
2. 既存を {idEvent: match} の辞書にする
3. 今回取得できた節(okRounds)の試合で辞書を上書き・追加する
4. 「今回取得した節に属するのに、レスポンスに無かった既存試合」は削除する
   （その節は正常に取れているので、消えたのは本物の日程削除）
5. 取得しなかった節の試合はそのまま残す ← ここが今回抜けていた
6. 辞書の値を kickoffJst 昇順（null は末尾）で並べて書き出す
```

**4と5の区別が肝。** 「取得した節の中で消えた」のは本物の削除、「そもそも取得していない節」は無関係なので触らない。この2つを混同すると、今回と同じか逆の事故になる。

`meta.okRounds` は「今回取得できた節」を指すので、そのままマージ範囲の判定に使える。

### 2-2. 激減ガード（これがあれば今回の事故は防げた）

書き出しの直前に検査する。

```
既存が存在し、かつ (新しい件数 < 既存件数 × 0.9) なら
  → 書き出さずに異常終了（exit code 非0）し、理由をログに出す
```

- 正しくマージしていれば件数は減らない。減ったら実装かデータの異常。
- `--full`（全38節取得）で正当に減るケースも考えにくいので、全モードで有効にしてよい。
- どうしても通したい場合のために `--allow-shrink` フラグを用意する。通常運用では使わない。

### 2-3. build_ics の大量キャンセルガード

`build_ics.py` に、1回の実行で**新たに CANCELLED にするイベント数**の上限を設ける。

```
新規CANCELLED件数 > 20 なら
  → ics_state.json を書き換えず、ics も生成せずに異常終了する
```

今回は1040件を静かに CANCELLED にした。この規模は日程変更ではありえないので、必ず異常として止める。既に `apply_cancellations()` 相当が `cancelled_count` を返しているので、そこで判定できる。

### 2-4. 試合総数の検算（軽い警告）

マスタの `totalRounds`（38）とクラブ数（20）から期待試合数380が出せる。マージ後の件数がこれと一致しない場合、`[warn]` を出す。中断まではしない（延期の差し替えで一時的にずれる可能性があるため）が、ログに残れば早期に気づける。

同じ検算を `simulate.py` にも入れる。`basedOnMatches + remainingMatches` が期待値と大きく食い違ったら警告する。今回のように「全4節のシーズン」を黙って計算するのを防ぐ。

## 3. テスト（必須）

## 4. 復旧後の確認

1. `j1/j2/j3_matches.json` がそれぞれ380件で、節1〜38が揃っていること。
2. `calendar.json` が1140件であること。
3. `j1_standings.json` の `basedOnMatches` が20（第1・2節ぶん）に戻っていること。
4. `j1_simulation.json` の `remainingMatches` が360前後であること。**30のままなら再計算されていない。**
5. `ics_state.json` の CANCELLED が0件、`seq` が2のエントリが1040件あること。
6. アプリの日程タブに第1節の結果が出ること。順位表の消化試合数が2になっていること。
7. `data/history/j1_probability_history.json` の 8/21 の `basedOnMatches` が20に直っていること。
8. **修正版で `--incremental` を1回走らせ、380件が維持されること。** ここまで確認して初めて Actions のスケジュールを再開する。
