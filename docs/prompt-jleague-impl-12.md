# 第12弾 実装指示：試合中のライブスコア表示

対象: `index.html`（フロントのみ。**バッチ・Pythonスクリプトは一切変更しない**）
前提ドキュメント: `docs/handoff-jleague-dashboard.md`、`docs/prompt-jleague-impl-10.md`（オンデマンド更新）

進行中の試合のスコアと経過時間を、TheSportsDB の `livescore.php` からブラウザが直接取得して表示する。

---

## 1. 前提（すべて実測で確認済み）

長らく保留だった3つの調査が2026-08-21〜22に全部片付いた。

| 調査 | 結果 |
|---|---|
| TheSportsDB は CORS 許可か | **許可**（2026-08-21 実機コンソールで確認） |
| Jリーグの試合が livescore に載るか | **載る**（2026-08-22 16:03 JST に実測） |
| 既存データと突き合わせられるか | **`idEvent` が完全一致。チーム名照合は不要** |

**したがってサーバーもPCも不要。フロントから直接ポーリングすればよい。** 保険として検討していたローカルバッチ方式（`fetch_live.py`）は不要になったので作らないこと。

### 実測したレスポンス（2026-08-22 16:03 JST・札幌 vs 大宮）

### 落とし穴（実測で判明）

**`updated` フィールドを使ってはいけない。** 実測時刻は UTC 07:03 / JST 16:03 だったのに `updated` は `08:03:33` で、UTCともJSTとも一致しない。タイムゾーンが不明なので、鮮度判定には**こちらの端末時刻**を使うこと。既存の「`strTimestamp` 以外の日時フィールドは信用しない」方針と同じ扱いにする。

**`intRound` が無い。** 節番号はレスポンスに含まれないので、節の情報が要る場面では `idEvent` で既存の `{league}_matches.json` を引くこと。

**世界中のサッカーが返ってくる。** 実測時は16件で、Jリーグ1件以外は全てオーストラリアのNPLだった。欧州の時間帯には桁が変わるはずなので、**必ず絞り込むこと**（次章）。

## 2. 置き場所（新しいタブは作らない）

当初は「速報タブ」を想定していたが、**専用タブは作らない。** クラブモードは既に6タブでスマホの下部バーとして上限、全体モードも3タブある。そこに増やすより、ライブスコアは**既存の画面にインラインで流し込むほうが自然**。

| 画面 | 表示 |
|---|---|
| クラブモード ホームタブ | 自クラブが試合中のとき、最上部に「試合中」カードを大きく出す |
| 全体モード 日程タブ | 進行中の試合の行に、スコアと経過時間をインライン表示 |

日付軸の日程タブは「今日どこがやっているか」を見る画面なので、そこがそのまま速報板になる。これがこの設計のいちばんの利点。

この判断を覆して専用タブにしたい場合は、上記2箇所の表示ロジックをタブに寄せるだけでよい（取得層は共通）。

---

## 3. 取得層

第10弾で `pickTargetRounds` / `parseEvents` / `mergeMatches` / `computeProvisionalTable` を UI から分離してあるので、その隣に追加する。純粋関数として書き、コンソールから単体で叩けるようにすること。

```
LIVE_LEAGUE_IDS = { "4633": "j1", "4824": "j2", "4967": "j3" }

pickLiveCandidates(matchesByLeague, now)
    → 自分のデータ上「試合中でありうる」idEvent の集合を返す
fetchLiveScores()
    → livescore.php を叩き、生の events 配列を返す（失敗時は null）
filterLiveEvents(events, candidateIds)
    → 自分に関係する試合だけに絞り、内部形式に変換して返す
```

### 3-1. ポーリングして良い条件（最重要）

**自分のデータ上で試合が進行中のときだけ叩く。** これを守らないと、試合の無い平日の昼にも延々とリクエストを投げ続けることになる。

```
候補 = {league}_matches.json の試合のうち、
       finished === false かつ
       kickoffJst <= 現在時刻 かつ
       現在時刻 < kickoffJst + 150分
```

- 150分はハーフタイムと追加時間を含んだ余裕。延長のあるカップ戦は対象外（リーグ戦のみ）なのでこれで足りる。
- 候補が0件なら**1回も叩かない**。タイマーも起動しない。
- 候補が0件になったらタイマーを止める。

### 3-2. 絞り込み

レスポンスは全世界のサッカーなので、2段で絞る。

1. `idLeague` が `4633` / `4824` / `4967` のいずれか
2. `idEvent` が 3-1 の候補集合に含まれる

**候補に無い `idEvent` は無視する。** レスポンス側にあってこちらに無い試合を勝手に足さないこと（カップ戦や誤登録が混ざる余地を消す）。

### 3-3. ポーリング間隔と停止条件

- 間隔は **60秒**。30秒より短くしない。
- **`document.visibilityState === "hidden"` の間は止める。** 可視に戻ったら即1回取得してから再開する。スマホでバックグラウンドのまま回し続けると電池を食う。ここは必ず実装すること。
- 連続失敗が3回に達したら止め、静かに「取得できませんでした」を出す。次に可視化されたときに再開してよい。
- 1セッションあたりの通算取得回数に上限（200回）を設ける。暴走時の保険。

### 3-4. 試合終了時の扱い

**livescore は試合が終わると載らなくなる可能性がある。** そこで:

- ある試合が `strStatus === "FT"` になった、または**候補なのに2回連続でレスポンスに現れなくなった**ら、その試合は終了とみなす。
- 進行中の試合が全部終わったら、**第10弾のオンデマンド取得を1回だけ自動実行する**（`eventsround.php`）。これが確定スコアの正本になる。
- この自動実行は第10弾のクールダウン（60秒）とは別枠にしてよいが、多重実行はしないこと。

## 4. 表示

### 4-1. ライブスコアを順位に混ぜない（重要）

**進行中のスコアを `computeProvisionalTable()` に渡してはいけない。** 45分時点の 0-2 はまだ結果ではない。順位表に反映していいのは、第10弾の `eventsround.php` 経由で `FT` として確定したものだけ。

同じ理由で、**ライブスコアを `localStorage` の `ondemand:` キャッシュに保存しない。** 進行中の値は揮発してよいメモリ上の状態として持つ。タブを閉じて翌日開いたときに「1-0 65分」が復活するのは明確なバグ。

### 4-2. 経過時間の表示

`strProgress` は `"45+4"` のような文字列で返る。

- **分数に変換しようとしない。そのまま出す。** `45+4` を数値パースすると壊れる。
- `strStatus` はそのまま表示に使うが、日本語ラベルに置き換えてよい。

| strStatus | 表示 |
|---|---|
| `1H` / `2H` | `{strProgress}′`（例: `67′`） |
| `HT` | `ハーフタイム` |
| `FT` | `終了` |
| 上記以外 | `strStatus` をそのまま出す（未知の値でも壊さない） |

未知のステータス（`ET` / `PEN` / `AET` / `POSTP` など）が来ても例外を投げないこと。

### 4-3. 見た目

- 進行中であることを、点滅する小さなドットなど**動きのある要素**で示す。静的なバッジだと更新されているのか分からない。
- スコアは確定値と視覚的に区別する（確定は通常表示、進行中はライブ色）。
- カード内に「◯◯:◯◯ 更新」を小さく出す。**端末時刻を使う**（`updated` フィールドは使わない。1章の落とし穴を参照）。
- 自クラブの試合は全体ビューでも強調する（既存のハイライトを流用）。

### 4-4. ホームタブの「試合中」カード

自クラブが試合中のときだけ、ホームタブの最上部に差し込む。「次の試合」カードはこのとき隠す（同じ試合が2箇所に出るため）。

```
　　● 試合中　67′
　　宮崎  1 - 2  湘南
　　　　　　　　　  16:47 更新
```

---

## 5. 失敗時の挙動

- ネットワークエラー・CORS失敗・JSONパース失敗のいずれも**アプリを落とさない**。直前に取得できた値を表示したまま、小さく「取得できませんでした」を出す。
- `{"events": null}` が返ることがある。これは「進行中の試合が世界のどこにも無い」意味なので、**エラー扱いにしない**（第10弾の `eventsround.php` とは解釈が違う点に注意）。候補があるのにこれが返る場合は、まだキックオフが反映されていないだけなので静かに次の周回を待つ。
- 取得層は例外を投げず `null` を返す形にする（既存の `getJsonOptional()` と同じ流儀）。

## 6. 確認手順

**試合中でないと確認できない項目があるので、Jリーグの開催日に実施すること。**

1. 試合が無い時間帯にアプリを開き、**`livescore.php` へのリクエストが1回も飛ばないこと**（開発者ツールのネットワークタブで確認）。
2. 試合中に開き、60秒間隔で取得されていること。
3. スコアと経過時間が表示され、更新時刻が動くこと。
4. **タブをバックグラウンドにするとリクエストが止まり、戻すと即座に1回走ること。**
5. 全体ビューの日程タブで、進行中の試合の行だけがライブ表示になっていること。他の日の試合は通常表示のままであること。
6. **進行中のスコアが順位表に反映されていないこと。** 順位は前回のバッチ／オンデマンド取得の値のままであること。
7. 試合終了後、自動でオンデマンド取得が1回走り、確定スコアと順位が更新されること。その後ポーリングが止まること。
8. ブラウザを閉じて翌日開き直したとき、**前日の進行中スコアが復活していないこと。**
9. オフラインにしてもアプリが落ちず、既存の表示が残ること。
10. 自クラブの試合が無く他クラブだけ試合中のとき、ホームタブにカードが出ず、全体ビューには出ること。

---

## 7. 実装順の推奨

1. `pickLiveCandidates()` / `filterLiveEvents()`（純粋関数。コンソールで検証できる）
2. `fetchLiveScores()` と失敗時のフォールバック
3. ポーリング制御（間隔・可視性・停止条件・上限）
4. 全体ビュー日程タブへのインライン表示
5. ホームタブの「試合中」カード
6. 試合終了検知 → オンデマンド取得の自動実行

3が終わった時点で、ネットワークタブを見ながら「叩くべきときだけ叩いているか」を確認してから4以降に進むこと。ここが緩いまま表示を作ると、後から直しにくくなる。
