# 第8弾 実装指示：昇格確率の推移 / 他会場インパクト / カレンダー(.ics)配信

対象リポジトリ: `jleague-app`（静的サイト＋Pythonバッチ）
前提ドキュメント: `docs/handoff-jleague-dashboard.md`（データ方針・確定した定数・禁止事項）

この3機能は独立に実装してよいが、**A と B は同じシミュレーション基盤を共有する**ため、A→B の順で着手すること。C は完全に独立。

---

## 全体の不変条件（既存方針。破らないこと）

- 日付・時刻は `strTimestamp`(UTC) 由来のもののみ信頼する。`data/processed/*_matches.json` の `kickoffJst` は既にこの規則で生成済みなので、そこから使う。`dateEvent` / `dateEventLocal` / `strTimeLocal` は参照しない。
- 順位付けは必ず `scripts/standings.py` の `rank_teams()` を通す。同順位クラスタの当該チーム間比較は「クラスタ内の全ペアが対戦済みのときだけ順序をつける」という不変条件があるので、独自の順位計算を書かない。
- Jリーグ公式由来のデータ（`data/processed/club_extra.json`、`data/tmp/` 配下）は配信対象に含めない。本指示で追加するデータはすべて TheSportsDB 由来＋自前マスタなので制約対象外。
- 新規ファイルは最初から Write ツールで作る（bash の `cp`/`touch` で作ったファイルは後から編集できなくなる既知の問題がある）。
- 出力先ディレクトリを増やしたら `scripts/build_dist.py` の `COPY_DIRS` / `TOP_LEVEL_FILES` に反映する。忘れると本番に出ない。

## A. 昇格確率の推移（履歴の蓄積とグラフ表示）

### A-1. 保存場所とフォーマット

新規ディレクトリ `data/history/` を作り、リーグごとに1ファイル。

```
data/history/j1_probability_history.json
data/history/j2_probability_history.json
data/history/j3_probability_history.json
```

**Render のディスクは揮発するので、履歴は必ずリポジトリ内に置きコミットすること。** Render 側の永続ディスクに書く実装にしてはいけない。

構造は列指向（transposed）にする。行指向（日付ごとにチーム配列）だとシーズン終盤に JSON が肥大化し、スマホでのパースが重くなる。

```json
{
  "meta": {
    "league": "j2",
    "season": "2026-2027",
    "schemaVersion": 1,
    "updatedAtJst": "2026-08-20T06:10:00+09:00"
  },
  "dates": ["2026-08-08", "2026-08-09", "..."],
  "basedOnMatches": [10, 10, "..."],
  "teams": {
    "137715": {
      "ja": "湘南ベルマーレ",
      "short": "湘南",
      "rank":          [7, 7, "..."],
      "points":        [3, 3, "..."],
      "champion":      [0.041, 0.038, "..."],
      "autoPromotion": [0.182, 0.171, "..."],
      "playoff":       [0.395, 0.402, "..."],
      "relegation":    [0.011, 0.013, "..."],
      "expectedPoints":[62.4, 62.1, "..."]
    }
  }
}
```

- すべての配列は `dates` と同じ長さで、インデックスが対応する。欠測は `null`。
- 確率は小数3桁に丸める（`round(x, 3)`）。`expectedPoints` は1桁。
- `promotionRules` にゾーンが定義されていないリーグ（J1 に `autoPromotion` が無い等）では該当キーを `null` 埋めではなく **キーごと省略**してよい。フロントは存在チェックすること。

### A-2. 追記処理

`scripts/simulate.py` の `main()` の末尾、`{league}_simulation.json` を書き出した直後に履歴追記を行う。別スクリプトに分けず simulate.py 内に閉じるほうが、update_all.py の手順を増やさずに済む。

- スナップショットのキーは **JST の日付**（`generatedAtJst` の日付部分）。
- **同じ日付が既にある場合は最後の値で上書きする**（append しない）。バッチが1日に複数回走るため、これをやらないと同日に何点も打たれてグラフが汚れる。
- 新しいチームがマスタに増えた場合、その `teams` エントリの各配列は過去分を `null` でパディングしてから追記する。長さがずれると描画側が壊れる。
- `--no-history` フラグを用意し、テストやアドホック実行で履歴を汚さずに回せるようにする。

### A-3. フロント表示

「スタッツ」タブ内、または新設のサブビューに折れ線グラフを1枚。

- **描画対象はチップで選択式**（回答済みの決定事項）。既定で自クラブを ON、他は OFF。タップで最大5クラブまで重ねられる。クラブ色（マスタの `color`）を線色に使う。
- 縦軸は確率（0〜100%）。表示する系列は `autoPromotion` を既定とし、`champion` / `playoff` / `relegation` に切り替えられるセレクタを置く。J1 のように該当ゾーンが無い場合はそのセレクタを出さない。
- 横軸は日付。ただし `basedOnMatches` が前日から変化していない日は「試合が無かった日」なので、点を打たず線だけ引く（マーカーが等間隔に並んで意味を持たなくなるのを避ける）。
- **自クラブの試合結果マーカーを重ねる。** `{league}_matches.json` から自クラブの `finished` な試合を拾い、その `kickoffDate` の位置に ○ / △ / ● の小さいマーカーを置く。「あの敗戦で確率が落ちた」が読めることがこの機能の主目的なので、これは必須。
- **序盤の注記は必須。** モデルは縮約(K=6)によりリーグ平均へ強く寄るため、開幕直後の確率変動は実力の変化ではなくモデルの不確実性を表している。グラフ下に常時「※ 開幕直後はモデルがリーグ平均に寄るため、確率の動きは実力変化を意味しません」の一文を出す。
- 実装は外部チャートライブラリを足さず、既存の描画方針（インライン SVG / Canvas）に合わせること。バンドルを増やさない。

## B. 他会場インパクト（次節の各試合が自クラブの確率をどう動かすか）

### B-1. アルゴリズム：1パス層別（重要）

**「各試合×勝分敗ごとに個別のシミュレーションを回す」実装にしてはいけない。** 10試合×3結果×3リーグ＝90回×10000試行となり非現実的。

正しい実装は、**既存の10000試行のループを1回だけ回し、各試行ごとに対象試合の結果を記録しておいて、後から試行を層別集計する**。

```
1. 対象試合集合 F を決める（B-2 参照）。
2. run_simulation() のループ内で、試行 t ごとに:
     - F の各試合の疑似結果を H / D / A に分類して記録する
       （例: outcomes[t] = "HDAHH..." のような固定長文字列、または int の配列）
     - 従来どおり各チームの最終順位・ゾーン到達を集計する
3. ループ終了後、F の各試合 f・各結果 o について:
     - outcomes[t][f] == o となる試行だけを抜き出し、
       その部分集合における各チームのゾーン到達率を再集計する
```

- 追加コストはメモリと最後の集計パスのみ。シミュレーション時間はほぼ変わらない。
- 条件付き確率としてもこちらのほうが正しい（他会場の結果同士の相関が自然に入る）。
- メモリ量の目安: 10000試行 × 10試合 = 10万要素。問題にならない。
- 実装上は、試行ごとの「チーム→到達ゾーン」も保持する必要がある。20チーム×10000試行のビット/バイト配列で持てば数MB以内に収まる。メモリが気になるなら、集計を「試合f・結果o」ごとのカウンタ配列（`counts[f][o][team][zone]`）にしてループ内で直接インクリメントする形にすれば、試行の保存自体が不要になる。**この後者を推奨**（メモリ一定、1パス完結）。

### B-2. 「次節」の定義（落とし穴）

**`round` の値で括ってはいけない。** 延期試合が実在するため、節番号と実際の日程はずれる。

対象試合集合 F の定義:

> 未消化試合のうち、`kickoffJst` が最も早いものを起点とし、その起点から **72時間以内** にキックオフする未消化試合すべて。

- 上限を設ける（例: 最大12試合）。ミッドウィーク開催などで窓が膨らんだ場合の暴発を防ぐ。
- `kickoffTbd` が true の試合は F に含めない（日時未定のものを「次節」に混ぜない）。
- F が空（シーズン終了・中断期間）の場合は、後述の出力ファイルを `"matches": []` で書き、フロントはセクションごと非表示にする。

### B-3. 出力

`data/processed/{league}_impact.json` を新規に出力する。

```json
{
  "meta": {
    "league": "j2",
    "generatedAtJst": "2026-08-20T06:10:00+09:00",
    "trials": 10000,
    "windowStartJst": "2026-08-22T14:00:00+09:00",
    "windowEndJst": "2026-08-25T14:00:00+09:00",
    "note": "確率差は0.5ポイント刻みの目安。層別により1条件あたり約3000試行のため誤差±1ポイント程度。"
  },
  "baseline": {
    "137715": { "champion": 0.041, "autoPromotion": 0.182, "playoff": 0.395, "relegation": 0.011 }
  },
  "matches": [
    {
      "idEvent": "2551799",
      "kickoffJst": "2026-08-22T14:00:00+09:00",
      "home": { "idTeam": "...", "short": "千葉" },
      "away": { "idTeam": "...", "short": "山形" },
      "trialCounts": { "H": 4120, "D": 2380, "A": 3500 },
      "conditional": {
        "137715": {
          "H": { "autoPromotion": 0.175, "playoff": 0.390 },
          "D": { "autoPromotion": 0.186, "playoff": 0.399 },
          "A": { "autoPromotion": 0.190, "playoff": 0.401 }
        }
      }
    }
  ]
}
```

- `conditional` は**全チーム分を持つ**。フロントで任意のクラブを選べる作りなので、自クラブ分だけに絞らない。
- サイズ目安: 12試合 × 3結果 × 20チーム × 4値。丸めれば 100KB 未満に収まる。超えるようなら `conditional` の値を `baseline` からの差分（小数3桁）だけにして圧縮してよい。
- `trialCounts` は必ず出す。特定の条件の試行数が極端に少ない場合（例: 500未満）、フロントはその条件の表示を伏せる判断ができる。

### B-4. フロント表示

「ホーム」タブに「今節の他会場」セクションを追加。

- 自クラブの試合は先頭に固定し、「勝てば ○%／引き分けなら ○%／負ければ ○%」と3値を並べる。
- 他会場の試合は、**自クラブへの影響が大きい順**に並べる（`max(conditional) - min(conditional)` の降順）。影響がほぼ無い試合は「その他」として折りたたむ。
- 表示は **0.5ポイント刻みに丸め、符号付きで差分表示**（`+1.5pt` / `-2.0pt` / `±0`）。決定事項として、小数第1位までの生の値は出さない。誤差 ±1ポイント程度なのに `+4.2%` と出すと嘘になる。
- セクション末尾に注記: 「※ シミュレーション上の目安です（誤差±1ポイント程度）」。
- 「%」ではなく「pt（ポイント）」表記を使い、確率そのものと差分を視覚的に区別する。

## C. カレンダー配信（.ics）

### C-1. 生成物

新規スクリプト `scripts/build_ics.py`。全60クラブぶんを生成する。

```
dist/ics/{idTeam}.ics
```

`build_dist.py` の `COPY_DIRS` にではなく、`build_dist.py` から `build_ics.py` を呼んで **dist 直下に直接生成**する形でよい（ソースツリーに 60 ファイルをコミットしたくないため）。`update_all.py` の手順にも `build_ics` を追加する。

対象試合は、そのクラブがホームまたはアウェイで出場する全試合（`{league}_matches.json` 全件、`finished` かどうかを問わない）。

### C-2. VEVENT の仕様

```
BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//jleague-app//JP
CALSCALE:GREGORIAN
METHOD:PUBLISH
X-WR-CALNAME:湘南ベルマーレ 2026-27
X-WR-TIMEZONE:Asia/Tokyo
X-PUBLISHED-TTL:PT12H
REFRESH-INTERVAL;VALUE=DURATION:PT12H
BEGIN:VEVENT
UID:2551707@jleague-app
DTSTAMP:20260820T000000Z
DTSTART:20260822T050000Z
DTEND:20260822T070000Z
SEQUENCE:0
SUMMARY:湘南 vs 千葉（J2 第3節）
LOCATION:レモンガススタジアム平塚
DESCRIPTION:キックオフ 14:00
STATUS:CONFIRMED
BEGIN:VALARM
TRIGGER:-PT1H
ACTION:DISPLAY
DESCRIPTION:湘南 vs 千葉
END:VALARM
END:VEVENT
END:VCALENDAR
```

**DTSTART は UTC(`Z`)で出す。** `kickoffJst` から UTC に戻すだけでよく、VTIMEZONE ブロックが不要になる。既存の「strTimestamp(UTC)のみ信頼」方針と完全に一致する。

`DTEND` はキックオフ+2時間。

### C-3. SEQUENCE の永続化（最重要）

**日時が変わったのに `SEQUENCE` を据え置くと、購読済みカレンダー側は更新を無視し、永久に古い日程が表示され続ける。** 延期試合は実在する（handoff の J3 琉球vs北九州の例）ため、これは必ず実装する。

`data/history/ics_state.json` を新設し、イベントごとの状態を永続化する。

```json
{
  "2551707": { "seq": 1, "dtstart": "20260822T050000Z", "summary": "湘南 2-1 千葉（J2 第3節）", "status": "CONFIRMED" }
}
```

生成時のルール:

1. 既存エントリが無ければ `seq: 0` で新規登録。
2. 既存エントリがあり、`dtstart` / `summary` / `status` のいずれかが今回の値と異なれば `seq += 1` して値を更新。
3. すべて同じなら `seq` 据え置き。
4. `ics_state.json` はリポジトリにコミットする（履歴と同じ理由で Render 側に置かない）。

### C-4. 消えた試合の扱い

前回の `ics_state.json` に存在するが今回の matches に存在しない `idEvent` は、**VEVENT を削除せず `STATUS:CANCELLED` にして残す**（同時に `seq += 1`）。VEVENT を単に消しても購読側のカレンダーからは消えないため、キャンセル通知として送る必要がある。

一度 CANCELLED にしたイベントは、以後の生成でも CANCELLED のまま出し続ける（シーズン終了までは残す）。

### C-5. SUMMARY の内容

決定事項として、**終了した試合はスコアを反映する**。

- 未消化: `湘南 vs 千葉（J2 第3節）`
- 終了済: `湘南 2-1 千葉（J2 第3節）`

スコアが入るタイミングで C-3 のルールにより自動的に `seq` が上がり、購読側に伝わる。1節あたり数イベントの更新なので同期負荷は問題にならない。

### C-6. 会場名（LOCATION）の解決

マスタの構造がリーグ間で異なるので分岐が要る。

- **J2**: 試合の `idVenue` → マスタの `venues[idVenue].ja`。
- **J1 / J3**: `venues` セクションが無い。ホームチームの `homeVenueJa` を使う。
- どちらも解決できない場合は `LOCATION` 行ごと省略する（空文字を出さない）。

既知の注意点として、味の素スタジアムは FC東京と東京Vの共用であり、中立地開催もあるため、`homeVenueJa` フォールバックは実際の会場と食い違うことがある。**不確実な場合は LOCATION を出さないほうが安全**なので、J1/J3 のフォールバックには `DESCRIPTION` 側に「会場は公式サイトで確認してください」の一文とクラブ公式へのリンクを添える。

### C-7. キックオフ時刻未定の試合

`kickoffTbd: true` の試合は、時刻付きイベントにせず **終日イベント**にする。

```
DTSTART;VALUE=DATE:20260822
DTEND;VALUE=DATE:20260823
SUMMARY:湘南 vs 千葉（J2 第3節・時刻未定）
```

終日イベントには `VALARM` を付けない（前日通知が意味を成さないため）。時刻が確定したら C-3 のルールで `seq` が上がり、時刻付きイベントに切り替わる。

### C-8. フロントの導線

- 「日程」タブの上部に「カレンダーに登録」ボタンを置く。
- リンクは `webcal://{ホスト}/ics/{idTeam}.ics`（`https://` ではなく `webcal://`。iOS / macOS でタップ一発の購読ダイアログになる）。
- Android / PC 向けに「URLをコピー」も併置する（`https://` のほう）。
- ボタン下に小さく注記: 「※ カレンダーアプリの更新間隔は端末側の設定に依存します。日程変更がすぐ反映されないことがあります。」iOS の購読カレンダーは既定の取得間隔が長いため、期待値を先に下げておく。

## テスト（必須）

既存のテストと同じ流儀（`scripts/test_*.py`、オフラインで完結）で追加する。

**A（履歴）**
- 同じ日付で2回追記しても配列長が増えず、値が後勝ちで上書きされること。
- 途中からマスタにチームが増えたとき、そのチームの配列が `null` で先頭パディングされ、全チームの配列長が `dates` と一致すること。
- `--no-history` で履歴ファイルが変化しないこと。

**B（インパクト）**
- 各試合について `trialCounts` の H/D/A の合計が `trials` と一致すること。
- 各チーム・各ゾーンについて、条件付き確率を `trialCounts` で加重平均すると `baseline` と一致すること（浮動小数の許容誤差内）。**これが層別集計が正しいことの最も強い検証になるので必ず入れる。**
- 未消化試合が0件のとき `matches: []` が出力され、例外にならないこと。
- 対象窓の決定が `round` ではなく `kickoffJst` の72時間窓で行われていること（延期試合を混ぜたフィクスチャで検証）。

**C（ics）**
- 日時を変えて2回生成すると `SEQUENCE` が 0 → 1 に上がること。変えなければ据え置きであること。
- 前回あったイベントが消えたとき `STATUS:CANCELLED` の VEVENT が出力に残ること。
- `kickoffTbd` の試合が `VALUE=DATE` の終日イベントになり、`VALARM` を持たないこと。
- 生成した ics が RFC5545 の基本構造を満たすこと（各行75オクテット以内への折り返し、`CRLF` 改行、`SUMMARY` 内のカンマ・セミコロン・バックスラッシュのエスケープ）。**日本語クラブ名を含む行の折り返しは、UTF-8 のマルチバイト境界を割らないこと。**

## 実装順の推奨

1. **A の履歴追記**（simulate.py への追記のみ。フロント無しでも動く）
2. **C の ics**（他機能と完全に独立。単独で価値が出る）
3. **B のインパクト**（simulate.py のループ構造に手を入れるため最後。A が動いていれば回帰に気づきやすい）
4. フロント3種をまとめて実装

各ステップごとに `python scripts/update_all.py` が最後まで通ることを確認してから次へ進むこと。
