# 第10弾 実装指示：オンデマンド更新（アプリから直接データ取得）

対象リポジトリ: `jleague-app`
前提ドキュメント: `docs/handoff-jleague-dashboard.md`

現在、データ更新は PC で `python scripts/update_all.py` を叩いたときにしか起きない。これを補うため、**アプリ側から TheSportsDB を直接叩いて最新の結果を取り込む「更新」ボタン**を追加する。

## 前提（確認済み）

**TheSportsDB はブラウザから直接 fetch できる。** 2026-08-21 に実機のコンソールで確認済み。

```js
fetch("https://www.thesportsdb.com/api/v1/json/123/eventsround.php?id=4824&r=3&s=2026-2027")
// → OK 件数: 10
```

CORS ヘッダーが許可されているため、プロキシもサーバーも不要。APIキー `123` は公開キーなので、フロントに埋め込んで問題ない。

## この機能の位置づけ（重要）

**バッチの置き換えではなく、バッチとバッチの隙間を埋める補助機能。** 取得するのは「今まさに行われている節の試合結果」だけで、それ以外はすべてバッチが作った静的JSONのまま使う。

やらないことを先に明示する:

- **全38節を取り直さない。** 114リクエストかかる。取るのは直近の節だけ。
- **昇格確率・スタッツ・ニュースは再計算・再取得しない。** モンテカルロをスマホで回さない。確率だけ新しくて他が古い状態は誤情報になる。
- **選手データ・公式サイト由来データには一切触れない。**

---

## 1. 取得対象の決定

**節番号で「次節」を決めてはいけない。** 延期があるため節と日程はずれる。第8弾の他会場インパクトと同じく、時間窓で決める。

```
1. 各リーグの matches から、kickoffJst が「現在時刻の -30時間 〜 +30時間」の範囲にある試合を集める
2. その試合が属する round の集合を取る（通常1つ、節をまたぐ時期は2つ）
3. round の集合が空なら、そのリーグは取得をスキップする
4. 上限は 1リーグあたり2節。3つ以上になった場合はキックオフが近い順に2つ選ぶ
```

- 前後30時間にしているのは、金曜夜の試合と日曜夜の試合の両方を1回の操作で拾うため。
- 3リーグ合計で最大6リクエスト。逐次実行し、**リクエスト間は300msあける**。
- 全リーグでスキップになった場合（中断期間など）は、ボタンを押しても「更新対象の試合がありません」と出して終了する。リクエストは投げない。

---

## 2. レスポンスの解釈（既存ルールを厳密に写すこと）

バッチ側 (`scripts/fetch_utils.py` / `scripts/time_utils.py`) と**同じ判定をフロントに実装する**。ここがずれると、オンデマンドとバッチで違う結果が出る。

| 項目 | ルール |
|---|---|
| 採用条件 | `strSeason === "2026-2027"` かつ `intRound !== "0"` |
| 日時 | **`strTimestamp`(UTC) のみ**。+9時間してJSTに変換 |
| 使ってはいけないフィールド | `dateEvent` / `dateEventLocal` / `strTimeLocal` |
| 完了判定 | `strStatus === "FT"` かつ `intHomeScore` が非null |
| チーム同定 | `idHomeTeam` / `idAwayTeam` をマスタの `idTeam` と直接照合 |

- **チーム名での照合はしない。** idTeam が全60クラブぶんマスタに入っているので名前マッチングは不要。idTeam がマスタに無い試合は無視する。
- 既存の試合との対応づけは `idEvent` で行う。
- レスポンスが `{"events": null}` または空配列だった場合は、**「その節に試合が無い」ではなく取得失敗として扱う**（バッチ側の `EMPTY` 分類と同じ思想）。その節の結果は捨て、既存データを維持する。

### マージ

- `idEvent` が既存の matches にあれば上書き（スコア・ステータス・キックオフ日時）。
- 既存に無い `idEvent` は追加する（日程差し替えで新しいイベントが発行されることがある）。
- **既存にあってレスポンスに無い試合は消さない。** 取得漏れと日程削除を区別できないため。

---

## 3. 順位の暫定計算（設計上の肝）

`scripts/standings.py` には「同順位クラスタの当該チーム間比較は、クラスタ内の**全ペアが対戦済みのときだけ**順序をつける」という不変条件がある。これを JS で微妙に違う形に再実装すると、バッチの順位とオンデマンドの順位が食い違うという最悪の事態になる。

**したがってフロント側では、当該チーム間比較を実装しない。**

```
暫定順位の判定順:  勝点 → 得失点差 → 総得点 → ここで打ち止め（以降は同順位）
```

- Python 側はこの先に当該チーム間比較があるため、**フロントのほうが順位が粗くなる**。これは意図的な劣化であり、誤情報ではない。「まだ順序をつけていない」だけなので安全側に倒れる。
- 同順位になった行は、バッチの `tiedWith` 表示と同じ見た目で並べる。
- **`playedDiff` は暫定順位でも必ず出す。** 消化試合数の差を隠さないという既存の不変条件は、暫定でも同じ。
- 暫定計算の対象は、オンデマンド取得したリーグのみ。取得していないリーグはバッチの `*_standings.json` をそのまま表示する。

---

## 4. 確率・シミュレーションの扱い

**再計算しない。** バッチの `*_simulation.json` の値をそのまま表示し続ける。

ただし、オンデマンドで結果が更新された状態では確率が古いことになるので、**確率を表示している全ての箇所に基準時刻を明示する**。

```
昇格確率  22.9%
（8/20 22:49 時点・その後の結果は未反映）
```

- 基準時刻は `simulation.json` の `meta.generatedAtJst` から取る。
- 他会場インパクト（`*_impact.json`）も同様。対象試合が既に終わっている場合は、その行を「終了」として畳む。

---

## 5. キャッシュと鮮度管理

`localStorage` に保存する。キーは `ondemand:{league}`。

```json
{
  "fetchedAt": "2026-08-21T19:35:12+09:00",
  "baseGeneratedAt": "2026-08-20T22:49:39+09:00",
  "matches": { "2551799": { "...": "マージ済みの試合データ" } }
}
```

- `baseGeneratedAt` は、取得時に読み込んでいたバッチ JSON の `meta.generatedAtJst`。
- **起動時に必ず比較する。** バッチ JSON の `generatedAtJst` が `baseGeneratedAt` より新しければ、そのキャッシュは役目を終えているので**破棄する**。これを忘れると、バッチで確定した正しいデータを古い暫定値が上書きし続ける。
- `localStorage` が使えない環境でも落ちないよう、読み書きは try/catch で囲む。

---

## 6. UI

### ボタン

- 置き場所は「ホーム」タブの上部と、全体ビューの「日程」タブの上部。
- **pull-to-refresh は実装しない。** スマホのスクロール操作で誤爆する。明示的なボタンにする。
- 連打対策として**最短60秒間隔**。クールダウン中はボタンを無効化し、残り秒数を出す。
- 取得中はスピナーとリクエストの進捗（`2/6`）を出す。数秒かかるため、無反応に見せない。

### 暫定であることの表示

オンデマンドで入った値は、バッチ由来の値と視覚的に区別する。

- 更新された試合のスコアの隣に小さいドット、または行に淡い背景。
- 順位表のヘッダに「暫定」バッジ。
- 画面のどこかに「最終更新 19:35（暫定・アプリから取得）」を常時表示。バッチの `deploy-time.txt` の表示とは別枠にする。

### 注記

> ※ 試合終了直後は反映されないことがあります。しばらく待って再度お試しください。

`eventsround.php` はステータスが `FT` に変わるまでラグがあることがあるため、この一文は必ず入れる。

---

## 7. 失敗時の挙動

- ネットワークエラー・CORS失敗・JSONパース失敗のいずれも、**アプリ全体を落とさない**。既存のバッチ値を表示したまま、「更新できませんでした」とだけ出す。
- 6リクエストのうち一部だけ成功した場合は、**成功したぶんだけマージする**。全部揃わないと反映しない、という作りにはしない。
- 既存の `getJsonOptional()` と同じ流儀で、取得層は例外を投げずに `null` を返す形にする。

---

## 8. 実装の分離（後の速報タブのため）

**取得層を独立させること。** 具体的には、以下を UI から切り離した純粋な関数として書く。

- `pickTargetRounds(matches, now)` — 取得対象の節を決める（1章）
- `parseEvents(json, master)` — レスポンスを内部形式に変換する（2章）
- `mergeMatches(existing, incoming)` — マージ（2章）
- `computeProvisionalTable(matches, master)` — 暫定順位（3章）

CORS が通ることが分かったので、同じ経路で `livescore.php?s=Soccer` を叩く**速報タブ**が実装可能になった。その際に上記の取得層をそのまま流用できるようにしておく。ただし**本指示書では livescore には触れない**（Jリーグの試合が実際に livescore に載るかが未確認のため。2026-08-21 19:00 のJ1第3節が最初の確認機会）。

---

## テスト（手動確認でよいが全部通すこと）

- 中断期間（前後30時間に試合が無い状態）でボタンを押しても、リクエストが飛ばずメッセージだけ出ること。
- 節をまたぐ時期（金曜と月曜に試合がある週）で、2節ぶんが対象になること。3節以上にならないこと。
- 一部のリクエストだけ失敗させたとき、成功したぶんが反映され、失敗したリーグは既存値のままであること。
- `{"events": null}` を返させたとき、その節の既存データが**消えない**こと。
- 暫定順位が「勝点→得失点→得点」で止まり、それ以上の順序をつけていないこと。同順位が同順位として表示されること。
- `playedDiff` が暫定順位表でも表示されていること。
- バッチ JSON を新しいものに差し替えたとき、古い `localStorage` キャッシュが破棄され、バッチ値が優先されること。
- 連打してもリクエストが多重に飛ばないこと。クールダウンが効くこと。
- 確率の表示に基準時刻（`8/20 22:49 時点`）が併記されていること。
- オフライン状態でボタンを押してもアプリが落ちないこと。

## 実装順の推奨

1. 取得層の4関数（UI無し。コンソールから叩いて検証できる形）
2. キャッシュと鮮度比較（5章）
3. 暫定順位（3章）
4. UI とクールダウン（6章）
5. 確率まわりの基準時刻表示（4章）
